# belFER — roadmap

Requirements live in `REQUIREMENTS.md`; the use-case and test-case IDs
referenced here live in `USE_CASES.md`.

Phases are ordered by dependency and by risk. Within a phase, subphases are
sized to be individually committable.

---

## Phase 0 — Foundations and the risky spike

**0.1 Backend skeleton**
`services/belFER/backend` with Bazel targets modelled on
`services/delFIN/backend/BUILD.bazel`. Copy the full explicit `deps` list, the
`platform_transition_filegroup`, and the `oci_image` `env` block verbatim —
those are non-obvious workarounds, not boilerplate. http4s Ember server,
`/health`, HOCON config. New port (delFIN holds 8080).

**0.2 Database**
Own Postgres schema, own Flyway location, `db/belFER/migrations` plus a second
`filegroup` in `db/BUILD.bazel`. delFIN's migrations are left untouched.

**0.3 Frontend skeleton**
`services/belFER/frontend`: Vite + React + Tailwind, the `@delfin/ui` alias,
Tailwind `content` covering `libs/ui`, a new port, and a `.bazelignore` entry
for its `node_modules`.

**0.4 Test-data directory**
`services/belFER/testdata/` with its `filegroup`, already in place. Anonymised
arkusz samples land in `arkusz/`; `private/` is gitignored for real data.

**0.5 ⚠ Timefold-under-Bazel spike — do this before Phases 1 and 2**

Solve a toy timetable end to end:

- the **whole solver module** as a `java_library` beside the Scala code, with
  a plain-Java interface and DTOs as the only boundary — no Timefold type
  reaches Scala
- `rules_java` added to `MODULE.bazel` if `java_library` is not already
  resolvable, and a `scala_library` → `java_library` dependency proven
- Timefold's transitive dependencies enumerated in `MODULE.bazel`
- reflection-based domain access rather than runtime bytecode generation
- running inside the built container image, not just under `bazel run`

**Outcome: green.** Timefold 1.16.0 compiles, configures and solves under
Bazel, called from Scala across a plain-Java boundary. `rules_java` 9.3.0 had
to be added to `MODULE.bazel` — Bazel 9 no longer provides `java_library`
natively — and `DomainAccessType` lives in `api.domain.common`, not
`config.solver`. Reflection-based domain access is used rather than Timefold's
generated bytecode.

The packaged layer carries the Timefold jar, and the migrations sit inside
`belfer_lib.jar` at `db/belFER/migrations/`, which is where Flyway looks. The
image builds and loads into Docker.

**Running the container is still unverified, and the reason is architecture.**
The image is cross-built for linux/amd64 — the Proxmox deployment target —
while an Apple Silicon machine runs an arm64 Linux VM under Colima with no
binfmt or Rosetta emulation, so it cannot exec the binary. Building an arm64
variant for local use was attempted and abandoned: `rules_oci` 2.3.0 reports
"No matching manifest found … for platform linux/arm64" for
`eclipse-temurin:17-jre-jammy`, even though `docker manifest inspect` lists
linux/arm64 in that index. That is a rules_oci limitation rather than anything
about belFER, and not worth absorbing here.

Two ways to close it when it matters: enable Rosetta in Colima
(`colima start --vz-rosetta`, needs the vz VM type), or run the image on the
amd64 host at deploy time. Until then the risk this check covers — reflection-
based domain access inside a sealed image — stays open, though the same code
path is exercised under `bazel test`, which is itself a sealed sandbox.

**Why first:** Timefold is the one load-bearing technology choice that could
fail outright under this repo's build constraints. If it cannot be made to
work, the solver strategy changes, and that is worth discovering in week one
rather than after two phases of data modelling. Everything else in the project
is ordinary CRUD-and-UI work with known patterns in the repo.

## Phase 2 — XML import

> **Runs after 1.6, before the rest of Phase 1.** The anonymised arkusz is
> already committed, so importing it validates the whole domain model against
> 797 real assignments at once — far faster, and far more honest, than
> hand-entering test data. If the lesson-line or PE model is wrong, this is
> where it shows, while it is still cheap to change and before the solver is
> built on top of it.

- **2.1** Parse and map the XML to the Phase 1 model
- **2.2** Import preview and unmapped-entity resolution — UC-24, UC-25
- **2.3** Re-import with a diff against current data — UC-26, UC-27

## Phase 3 — Solver

- **3.1** Planning domain and Timefold wiring, built on the 0.5 spike. The
  solver takes **one interval** and the assignments active in it (§4.1); the
  constraints themselves are not time-aware
- **3.2** Hard constraints — CT-01 … CT-17, and CT-21 as the regression guard
- **3.3** Soft constraints and user-editable weights — CT-18 … CT-20, UC-04
- **3.4** Async job: start, progress, early stop, configurable timeout,
  persistence — UC-28 … UC-31, UC-34
- **3.5** Infeasibility explanation and run comparison — UC-32, UC-33

> 3.5 is not polish. The school's instance is assumed solvable, so an
> infeasible run means a mistake somewhere in ~500 assignment rows — and a bare
> "no solution" would leave the user with nothing to act on.

## Sequencing notes

- **0.5 gates everything.** Do not build Phases 1–2 on the assumption that
  Timefold works under Bazel.
- **Phase 2 runs early**, straight after 1.6, for the reason given above: it is
  the cheapest way to find out whether the domain model survives contact with
  real data. 1.7 and 1.8 follow it.
- **1.8 is the first checkpoint worth showing the school.** Before it the UI is
  data entry and only its shape can be judged; from 1.8 the app starts telling
  the planner something they did not already know. Phase 4 is the first point
  at which an actual timetable can be looked at.
- **Phase 3 needs realistic data.** The instance is assumed solvable, so the
  open question is not *whether* a plan exists but how long it takes to find
  one and whether the default weights produce a plan the planner actually
  likes. Toy fixtures verify the constraints; only a real year's worth of
  assignments will settle runtime and weighting. Getting one real dataset into
  `testdata/` early is worth more than any amount of synthetic testing.
- **The solver module is Java.** Constraint tests (`CT-*`) are therefore Java
  tests against the `ConstraintProvider`, not Scala tests — they are the
  cheapest and most valuable tests in the project, so keep them close to the
  engine.
